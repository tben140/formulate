# Surface: mobile app

`apps/mobile` — Expo SDK 57, React Native 0.86, Expo Router, NativeWind v5.

## Stack

|          |                                                                            |
| -------- | -------------------------------------------------------------------------- |
| Runtime  | Expo SDK 57 / React Native 0.86, New Architecture only                     |
| Routing  | Expo Router, with `typedRoutes` enabled                                    |
| Styling  | NativeWind v5 preview, sharing the same Tailwind v4 token file as web      |
| Fetching | TanStack Query over the shared Storefront client                           |
| Images   | `expo-image`                                                               |
| Builds   | EAS; `app.config.ts` rather than `app.json` so it can read the environment |

## Screens

| Screen          | File                        |
| --------------- | --------------------------- |
| Collection list | `app/index.tsx`             |
| Product detail  | `app/products/[handle].tsx` |

Both render the shared `components/site-footer.tsx` at the end of scrollable
content — `ListFooterComponent` on the list, end of the `ScrollView` on detail —
rather than docked to the viewport. That matches what web and Liquid actually do,
and docking would permanently spend vertical space that is scarcer on a phone.

That footer carries a documented coupling: `-mx-4` cancels the `p-4` its parent
scroll container applies, so the top border reaches the screen edges while the
text stays aligned with the content above. It is a shared component _because_ of
that assumption, not in spite of it.

## Data access

`lib/storefront.ts` reads `EXPO_PUBLIC_SHOPIFY_*`. The prefix is required, not
merely conventional: Metro inlines those values at bundle time, and **the bundle
is the client**. A public Storefront access token is designed for exactly this —
it is scoped to storefront reads and rate limited per buyer IP.

An Admin API token must never appear here. There is no server in this app to hide
one behind.

`lib/queries.ts` wraps the shared client in TanStack Query. It lives in the app
rather than in `packages/shopify` because the web app fetches in Server
Components and would never call it; putting TanStack in the shared package would
force a dependency on `apps/web` that it has no use for. What _is_ shared is the
client, the query documents and the generated types.

`request()` returns a Result rather than throwing, so the query functions convert
a failed Result into a thrown `Error` — that is the contract TanStack Query needs
to drive `isError`.

## Metro configuration

`metro.config.js` is short, and what is _absent_ matters: no `watchFolders`, no
`resolver.nodeModulesPaths`, no `resolver.disableHierarchicalLookup`. Expo SDK 52
and later detect the monorepo and configure Metro themselves. Setting those
manually now causes resolution bugs rather than fixing them.

The workspace uses `node-linker=hoisted` (`.npmrc`) because Metro and autolinking
both expect a flat, real-directory `node_modules`. This is the single required
deviation from pnpm's defaults in an Expo monorepo.

## Checkout — what the spike established

The SHO-56 spike lives on `spike/sho-56-checkout-kit` and is **not for merge**.
It answered the handoff question; the real implementation gets built fresh.

Verified on an iPhone 17 Pro simulator:

- `@shopify/checkout-sheet-kit` 3.8.1 runs on Expo SDK 57 with **no config
  plugin** — autolinking picks it up through `expo prebuild`. It cannot run in
  Expo Go, so **a development build is mandatory**.
- A real test order completed through the native sheet: Shopify **#1001**, PAID,
  £774.90, producing an active Recharge subscription (#854707192, £24.95 every
  30 days).
- Lifecycle ordering matters. `completed` fires carrying the order id at
  14:54:27; `close` fires afterwards at 14:55:41 when the confirmation screen is
  dismissed. **Cart-clearing logic must account for that ordering**, or a `close`
  handler will undo a correct clear.
- The `completed` event returns `gid://shopify/OrderIdentity/{id}`, which is
  **not** the Admin API's `gid://shopify/Order/{id}`.

Two fixes were needed to keep the workspace green:

- `colorScheme` takes the `ColorScheme` enum, not a string literal.
- A typing shim for `Error.captureStackTrace`. The package sets
  `"types": "src/index.ts"`, pointing TypeScript at raw source, so `skipLibCheck`
  does not apply and its own source is typechecked here. The shim is narrower
  than pulling `@types/node` into a React Native app, which would wrongly imply
  Node globals exist at runtime.

See [ADR 0006](adr/0006-checkout-handoff-differs-per-surface.md).

## Native project directories

`ios/` and `android/` are gitignored. They are generated by `expo prebuild` and
are not the source of truth; `app.config.ts` is. iOS builds need CocoaPods
installed locally, because `pod install` links the native modules autolinking
discovered.

## Known constraints

- **NativeWind v5 is pre-release** (`5.0.0-preview.4`), chosen so both React
  surfaces share one Tailwind v4 token file — see
  [ADR 0003](adr/0003-nativewind-v5-and-tailwind-v4.md).
- **`lightningcss` is pinned to `1.30.1`** workspace-wide. Anything newer fails
  at Metro bundle time and never at install time — see
  [ADR 0004](adr/0004-pin-lightningcss-to-1-30-1.md).
- **`expo-env.d.ts` is generated and gitignored**, so a fresh clone lacks the
  `*.css` module declaration. The committed `nativewind-env.d.ts` carries the
  same reference directive to compensate. Do not remove it.
